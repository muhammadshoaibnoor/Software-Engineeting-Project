\section{Introduction}
Restaurants, such as pizza shops, often face difficulties in managing orders, sales, and inventory, especially when operating multiple branches. A Point-of-Sale (POS) system helps overcome these challenges by simplifying the process of taking and managing orders, and organizing operations even during busy hours. It provides a centralized view of menus and stock for each branch, ensuring that only available items are shown. The system tracks popular dishes, alerts staff when ingredients run low, and maintains consistent pricing across branches, reducing errors and speeding up service.

\section{Problem Statement}
Many pizza shops currently rely on manual management, which often leads to several problems. Orders are written by hand, causing mistakes such as wrong items, missing custom requests, or miscommunication between waiters and kitchen staff. In multi-branch setups, a waiter may take an order for an item unavailable at their branch. Manual billing and order tracking are time-consuming, especially during busy hours, resulting in delays. Without a POS system, generating accurate sales reports, identifying best-selling items, and applying deals or discounts effectively is difficult, which may reduce customer satisfaction and revenue.

\section{Project Objectives}
The following objectives define the main goals and expected outcomes of the project.

\begin{enumerate}
    \item To design a multi-branch compatible Point-of-Sale (POS) system for pizza shops.
    \item To allow the admin to create, update, and delete menu items for each branch.
    \item To manage inventory of both raw ingredients and prepared items in real time.
    \item To provide automatic deal recommendations based on user selections.
    \item To ensure efficient order processing and accurate billing.
\end{enumerate}

\section{Methodology}

This project follows the \textbf{Agile Scrum methodology}. Work is divided into \textbf{short, time-boxed sprints}, each focusing on completing specific tasks. At the end of every sprint, progress is reviewed, feedback is collected, and the plan is improved for the next sprint. Scrum allows flexibility, so changes in requirements can be included without affecting the whole project.

The project spans \textbf{one year}, from \textbf{October 2025 to September 2026}, and is divided into multiple sprints and key activities:

\begin{itemize}
    \item \textbf{Requirement Analysis (Oct 2025 – Jan 2026):}\\
    The project began with the first meeting with the Requirement Provider to understand the project vision. Product backlog creation and refinement followed. In the second meeting, the system flow was finalized, and the SRS along with context and use case diagrams was prepared.
    
    \item \textbf{Development Sprints (Jan 2026 – May 2026):}\\
    Sprint 1: Core Order Management \\
    Sprint 2: Kitchen Module \\
    Sprint 3: Billing \& Payment Module \\
    Sprint 4: Deals \& Recommendations \\
    Sprint 5: Inventory Management \\
    Each sprint focused on designing, implementing, and testing individual modules step by step.
    
    \item \textbf{Advanced Modules and Admin Features (Apr 2026 – May 2026):} \\
    Sprint 6: Admin Module development \\
    Sprint 7: System Integration \& Testing
    
    \item \textbf{User Testing and Final Enhancements (Jun 2026 – Jul 2026):}\\
    Sprint 8: User Acceptance Testing (UAT) \\
    Sprint 9: Final Enhancements & Bug Fixes
    
    \item \textbf{Deployment, Monitoring, and Documentation (Jul 2026 – Sep 2026):}\\
    Sprint 10: Minor Enhancements & Bug Fixes \\
    Sprint 11: Monitoring & Performance Evaluation \\
    Sprint 12: Final Deployment \\
    Sprint 13: Documentation
\end{itemize}

The team held regular \textbf{daily stand-up meetings} to share updates and solve problems quickly. At the end of each sprint, progress was reviewed, feedback was collected, and plans were updated for the next sprint.

This approach helped the team work in a clear and step-by-step way. Each part of the system was completed one by one, and the Requirement Provider and users were involved throughout. Using Scrum for the full year made it easier to manage tasks, avoid mistakes, and deliver a high-quality POS system that meets user needs.

\section{Tools and Technologies}

The following key tools and technologies are used for the development of the POS system:\\

\begin{itemize}
\item \textbf{Backend / Core Logic:} The system backend is developed using C++.
\vspace{0.3cm}

\item \textbf{Frontend / User Interface:} HTML, CSS, and JavaScript are used to create the interfaces for the waiter, cashier, and kitchen staff, ensuring a responsive and user-friendly experience.
\vspace{0.1cm}

\item \textbf{Database:} MySQL stores all critical data including menu items, orders, inventory, and sales reports.
\vspace{0.3cm}

\item \textbf{Real-time Communication:} WebSocket or socket programming is used to send order status updates instantly between the waiter, kitchen, and cashier terminals.
\vspace{0.3cm}


\item \textbf{Payment Processing:} The system integrates local online payment gateways for secure online transactions. Cash payments are entered manually through the POS.
\vspace{0.3cm}

\item \textbf{Version Control:} Git along with GitHub is used to track code changes and support collaboration among the development team.
\vspace{0.3cm}

\item \textbf{Project Management / Scrum:} Jira or Trello is used to manage sprints, backlogs, and tasks efficiently throughout the development cycle.
\vspace{0.3cm}

\item\textbf{Deployment Platform:} The POS system runs on Windows or Linux desktops for use by staff in the restaurant.
\vspace{0.3cm}

\item \textbf{Documentation and Diagrams:} LaTeX along with UML tools such as draw.io or StarUML is used to prepare the SRS, context diagrams, and use case diagrams.
\vspace{0.3cm}

\item \textbf{Prototype Design:} Figma is used to design the system interface and workflow before actual development, allowing visualization and early feedback.
\end{itemize}
